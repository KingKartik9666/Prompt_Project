1. Pipeline at a glance
The pipeline runs P1 router, then P2 explainer, then P3 claim extractor plus a simulator check with one repair retry, then P4 practice. The file says it has the same control flow as run() in code/workflow.py. [app/crates/desktop/src/pipeline.rs:1-2]
Every stage is streamed to the web view as a JSON event that carries the question&apos;s id. [app/crates/desktop/src/pipeline.rs:21-25]
Each question runs on a new OS thread with a new LLM client. The provider, key and model are resolved when the question is asked, not at app start. [app/crates/desktop/src/main.rs:259, 268-275; app/crates/desktop/src/config.rs:179-184]
The four prompts are compiled into the executable with include_str! from prompts/final/, so the app reads no prompt files at run time. [app/crates/desktop/src/prompts.rs:24-31]

2. Stage by stage
P1 router
Inputs: the trimmed question and the level. The host maps any level other than &quot;intermediate&quot; to &quot;beginner&quot;. [app/crates/desktop/src/main.rs:254-258; app/crates/desktop/src/pipeline.rs:30-34]
If the answer does not parse to a non-empty JSON object, the route stage is marked as an error and the run ends with the final message &quot;The router&apos;s answer was not valid JSON. Please try again.&quot; [app/crates/desktop/src/pipeline.rs:35-40]
The UI shows any final message under the heading &quot;Not a quantum-algorithm question&quot;, so the invalid-JSON message appears under that heading too. [app/crates/ui/src/tutor.rs:250-251; app/crates/desktop/src/pipeline.rs:136-141]
Scope is read with Python-style truthiness of in_scope. A missing algorithm becomes the text &quot;null&quot;. A non-string value is written as JSON. [app/crates/desktop/src/pipeline.rs:41-43; app/crates/desktop/src/prompts.rs:183-201]
Out of scope: the explain, verify and practice stages are sent as skipped, and the run ends with the fixed text &quot;I can help with quantum algorithms (Bell states, Deutsch-Jozsa, Grover). Please ask a question about one of them.&quot; [app/crates/desktop/src/pipeline.rs:9-10, 51-56]
Parameters are normalised in code. grover2: marked defaults to &quot;11&quot;, and an invalid value becomes &quot;11&quot;. deutsch_jozsa: n defaults to 2 and is clamped to 1-3; f_kind defaults to &quot;balanced&quot;, and &quot;constant&quot; maps to &quot;constant0&quot;. bell has no parameters. Any other algorithm is not verifiable. [app/crates/qcore/src/lib.rs:407-438; app/crates/desktop/src/pipeline.rs:44-45]
The host uses only in_scope, algorithm, params, false_premise (default &quot;none&quot;) and intent (default &quot;explain&quot;). language and injection_attempt are only shown as tags in the UI. [app/crates/desktop/src/pipeline.rs:41-62; app/crates/ui/src/tutor.rs:231-236]
The route event carries the router JSON, the normalised params, a verifiable flag, the call time in seconds and a clean flag. clean is false when the JSON had to be cut out of surrounding text. [app/crates/desktop/src/pipeline.rs:46-49; app/crates/desktop/src/prompts.rs:167-181]
P2 explainer
The explainer runs at most twice (attempt 0 and attempt 1). [app/crates/desktop/src/pipeline.rs:69]
Inputs filled in: the algorithm name; the params as Python-style JSON; level; false_premise; intent; the question; and verifier_feedback, which is empty on the first attempt. [app/crates/desktop/src/pipeline.rs:63-82]
If the answer is not a parsable, non-empty JSON value, the raw text is kept as the explanation, and the UI shows it as one paragraph. [app/crates/desktop/src/pipeline.rs:84-87; app/crates/ui/src/tutor.rs:294-295]
If the algorithm is not verifiable, a verification event with ok: null and the note &quot;Not checkable by the simulator: shown as unverified.&quot; is sent, the verify stage is skipped, and the loop ends. The UI heading is &quot;Explained, not verified&quot;. [app/crates/desktop/src/pipeline.rs:90-94; app/crates/ui/src/tutor.rs:262-269]
P3 claim extractor, simulator check and repair
P3 receives the parsed explanation re-serialised as Python-style JSON, or the raw text when parsing failed. [app/crates/desktop/src/pipeline.rs:96-97]
Only probabilities is taken from P3. The ground truth always comes from the router&apos;s normalised params, never from P3&apos;s echo of them. [app/crates/desktop/src/pipeline.rs:99-102]
The check uses an absolute tolerance of 0.02. [app/crates/desktop/src/pipeline.rs:102; app/crates/qcore/src/lib.rs:518-557]
Values accepted: numbers, booleans, and strings such as &quot;0.5&quot;, &quot;1/2&quot; and &quot;50%&quot;. Keys are normalised by keeping only 0 and 1 characters. An unparsable value is a mismatch. No probabilities at all gives &quot;no final probability stated&quot;. For Deutsch-Jozsa only P(all zeros) on the n input bits is compared, plus checks on key length and on the sum. [app/crates/qcore/src/lib.rs:395-398, 440-458, 519-557]
Ground truth is the simulated probabilities rounded to 6 decimals with zero entries dropped, the same rule as the Python simulator. [app/crates/qcore/src/lib.rs:122-141; code/quantum_sim.py:30-33]
On a pass, the loop ends. On a fail, the feedback is &quot;Verifier feedback: a simulator found these errors in your previous answer: &lt;mismatches joined by &apos;; &apos;&gt;. Correct result: &lt;truth as a Python dict repr&gt;. Fix the explanation.&quot; P2 then runs once more. [app/crates/desktop/src/pipeline.rs:106-113; app/crates/qcore/src/lib.rs:474-478]
A repair event is sent only after the first failure. UI headings: &quot;Verified by the simulator&quot;, &quot;Corrected, then verified&quot;, or &quot;The numbers do not match&quot;. [app/crates/desktop/src/pipeline.rs:114-116; app/crates/ui/src/tutor.rs:273-277]
After a failed second attempt there is no third attempt. The run goes on to P4 with the simulator truth. [app/crates/desktop/src/pipeline.rs:69, 103, 119-131]
P4 practice and the end of a run
Inputs: algorithm, params, level, truth and explanation. truth is the simulator result as JSON, or &quot;not available&quot; when no check ran. The explanation is serialised as JSON, so a raw-text explanation becomes a JSON string. [app/crates/desktop/src/pipeline.rs:120-131]
The parsed output is sent as a practice event, with null when it does not parse. The UI shows question, hint and answer_key only when the data is an object, so an unparsable P4 answer silently produces no practice section. [app/crates/desktop/src/pipeline.rs:132-135; app/crates/ui/src/tutor.rs:350-364]
The done event carries final (null on a normal run), the models used, and the total seconds rounded to 0.1 s. The UI footer reads &quot;Answered by {models} in {seconds} s&quot;. [app/crates/desktop/src/pipeline.rs:139-141; app/crates/ui/src/tutor.rs:369-372]
An error at any stage ends the run with an error event. The UI marks the active stages as failed. Its error verdict is checked first, so it replaces anything already shown, including a verification result. [app/crates/desktop/src/pipeline.rs:140-143; app/crates/ui/src/state.rs:204-213; app/crates/ui/src/tutor.rs:245-249]

7. Key validation before saving
Order of steps, all on a worker thread: [app/crates/desktop/src/main.rs:161-191]
(1) the host trims the key; (2) resolves the provider; (3) checks the format: 20-400 characters, no whitespace or control characters; (4) checks the key live with the provider; (5) stores it in Credential Manager, trimming and checking the format again; (6) makes the provider active; (7) sends status with key_saved: true. [app/crates/desktop/src/main.rs:164, 171-186; app/crates/desktop/src/config.rs:191-199, 210-217, 230-238]
On failure the host sends key_error with a message scrubbed of the key, plus the provider id. needs_provider is true only for provider-resolution errors. [app/crates/desktop/src/main.rs:173-176, 188; app/crates/ui/src/state.rs:150-156]
